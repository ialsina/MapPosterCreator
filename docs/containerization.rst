Containerization
================

The repository includes a Docker image for the HTTP service. The image is
based on Python 3.11 slim, installs GDAL, GEOS, and PROJ build dependencies,
and starts Uvicorn on port 8000.

Current build limitation
------------------------

The current ``Dockerfile`` copies and installs a root-level
``requirements.txt``, but that file is not present in this checkout.
Consequently, an unmodified checkout cannot currently complete
``docker build``. Runtime dependencies are declared in ``pyproject.toml``;
the Dockerfile must be aligned with that packaging source (or a requirements
file must be added) before relying on the commands below.

There is a second limitation in the automatic image setup: every Dockerfile
path that invokes ``scripts/setup.sh`` passes ``--skip-colors``, but the
runtime colour loader currently opens ``docc_colors.json`` unconditionally.
Thus ``/colors`` and poster creation require prepared build or mounted data
that includes this file, even though it represents an optional extended
palette in the setup script. ``/health`` does not validate colour data.

The repository also contains no Docker Compose file or CI/CD workflow.
The ``ghcr.io/<owner>/<image>:<tag>`` text in the Dockerfile is a tagging
convention, not an implemented publishing pipeline.

Image build and data pipeline
-----------------------------

After the packaging issue above is fixed, the basic build command is:

.. code-block:: bash

   docker build -t map-poster-creator .

The image needs generated geographic indexes. It chooses a build-time source
in this order:

1. A non-empty ``data/`` directory in the build context containing
   ``geofabrik_tree.nw``.
2. The directory named by the ``DATA_DIR`` build argument.
3. Data generated by ``scripts/setup.sh``.

``data/`` is ignored by Git but is deliberately included in the Docker build
context. Pre-generating it avoids repeated network downloads:

.. code-block:: bash

   bash scripts/setup.sh --tiny --non-interactive --output data
   docker build -t map-poster-creator .

If no usable data is supplied, the default build runs the setup pipeline in
tiny mode while skipping colours. Tiny mode creates the Geofabrik region
index needed for coordinate-based requests, but omits city and geoBoundaries
datasets. Because of the colour-loader limitation above, automatically
generated data is not sufficient for poster endpoints.

Set ``NO_TINY=true`` to request the full six-step data setup:

.. code-block:: bash

   docker build --build-arg NO_TINY=true -t map-poster-creator:full .

``DATA_DIR`` must identify a directory available inside the build context;
the selected data is copied into the image and changes require a rebuild:

.. code-block:: bash

   docker build \
     --build-arg DATA_DIR=./prepared-data \
     -t map-poster-creator:prepared .

Run the service
---------------

The container defaults are:

* API address: ``0.0.0.0:8000``
* data: ``/app/data``
* generated posters: ``/app/output``
* logs: ``/app/logs``

A typical persistent deployment mounts all three writable directories:

.. code-block:: bash

   docker run --rm -p 8000:8000 \
     -v "$(pwd)/data:/app/data" \
     -v "$(pwd)/output:/app/output" \
     -v "$(pwd)/logs:/app/logs" \
     map-poster-creator

The runtime variables ``MAPOC_DATA_DIR``, ``MAPOC_OUTPUT_DIR``, ``LOG_DIR``,
and ``LOG_LEVEL`` can change these locations and console verbosity. Mount
volumes at the matching custom paths when overriding them.

Entrypoint data preparation
---------------------------

Before starting Uvicorn, ``docker-entrypoint.sh`` creates the data and output
directories and searches for usable data in this order:

1. ``/app/data_source`` populated during the image build.
2. ``MAPOC_DATA_DIR``, including a mounted volume.
3. A fresh tiny setup written to ``MAPOC_DATA_DIR``.
4. Legacy fallbacks at ``/app/data_built`` and ``/root/.mapoc``.

When build data is selected, it is copied into ``MAPOC_DATA_DIR`` unless that
destination is already complete. A valid ``geofabrik_tree.nw`` must exist and
be at least 100 KB; an undersized destination copy is replaced. Failure of the
final size check stops the container.

Health and readiness
--------------------

The image health check calls ``http://localhost:8000/health`` every ten
seconds after a 40-second start period. It considers the container healthy
only when the JSON response contains ``\"data_ready\": true``.

The endpoint itself returns HTTP 200 while data is unavailable, with
``status`` set to ``starting``. Consumers should therefore inspect
``data_ready`` rather than treating any HTTP response as readiness. See
:doc:`service` for the complete service interface.
